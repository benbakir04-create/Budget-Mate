# 0005: منهجية «ركيزة»: واجهة ثابتة على GitHub Pages + Supabase، بلا خادم تطبيقات

**التاريخ:** 16 نوفمبر 2026 · **الحالة:** معتمد (منهجية علي «ركيزة»)
**يحلّ محل:** خادم Express + Prisma المستقل الموصوف في `TECHNICAL_ARCHITECTURE.md`. ADR 0001 (Next.js) و0003 (Supabase مع Next.js) صارتا تاريخًا.

## السياق

وازن تطبيق مالي تشاركي، مساره الأول عائلي، وسوقه الجزائر بعملة الدينار:

- **البيانات:** كل شيء خلف تسجيل دخول.
- **العزل بين الجهات:** كل عائلة أو صندوق يرى بياناته فقط (multi-tenant).
- **الحجم:** عشرات إلى مئات المستخدمين في مرحلة التجربة.
- **الظهور العام:** لا حاجة لمحركات البحث.

البنية الحالية ثلاث قطع: واجهة React 18 بـ JavaScript، وخادم Express + Prisma يحتاج استضافة دائمة، وقاعدة على Supabase. يريد علي أقل عدد من الخدمات، بكلفة وصيانة صفر قبل أي استثمار.

**فحص حدود المنهجية (§2):**

- المسار العائلي داخل الحدود تمامًا.
- **عناصر لاحقة تُراجع عند وصولها:**
  - **المستشار المالي الذكي:** استدعاء نموذج ذكاء اصطناعي. يصلح عبر Edge Function إن بقي خفيفًا، وإلا يُناقش بديل.
  - **الدفع (Chargily / Google Play):** يحتاج webhook وسرًّا في الخادم، عبر Edge Function.
  - **تصدير Excel لمسار الأعمال:** يصلح في المتصفح أو عبر Edge Function.

لا شيء منها في نطاق الإصدار العائلي الأول.

## القرار

1. **الواجهة:**
   - Vite + React + TypeScript (strict) + Tailwind، صفحة واحدة بـ `HashRouter` و`base: './'`.
   - RTL عربي أولًا، مع الإبقاء على نظام التصميم الحالي (الزمردي، Readex Pro، الشريط السفلي).
   - الانتقال إلى TypeScript وReact 19 وTailwind 4 يتم تدريجيًا مع إعادة ربط الخدمات، لا دفعة واحدة.
2. **البيانات والدخول:**
   - Supabase (PostgreSQL + Auth + Storage). المتصفح يحمل **المفتاح العام فقط**.
   - كل صلاحية في RLS ودوال `security definer` بـ `search_path=''`.
   - الأدوار (مالك / شريك) من `app_metadata` لا من بيانات يكتبها المستخدم.
   - جدار الخصوصية: الشريك لا يرى أقسام المالك الخاصة ولا يعدّل ولا يحذف.
3. **العمليات المالية** (تمويل صندوق كـ `transfer`، صرف، اعتماد طلبية):
   - دوال RPC في معاملة واحدة، تتحقق من الصلاحية وتكتب **سجل التدقيق** المطلوب في CLAUDE.md.
   - قواعد العمل الحالية تنتقل كما هي: أنواع `income`/`expense`/`transfer`، وحساب الإجماليات، وحدود الميزانية (أقل من 75% / من 75% / من 100%).
4. **العمليات المميّزة:** Supabase Edge Functions، منها **التصدير إلى Google Sheets**:
   - زر يطلقه المالك وحده، يختار فيه الفترة والجداول.
   - الكتابة بحساب خدمة مفتاحه في أسرار Supabase. لا مزامنة تلقائية.
5. **الاستضافة:**
   - مستودع الكود `Budget-Mate` يبقى **خاصًا**.
   - الموقع يُنشر إلى **مستودع عام منفصل** لا يحوي إلا ملفات البناء، عبر `peaceiris/actions-gh-pages` بـ `force_orphan`، فلا حاجة لاشتراك GitHub مدفوع.
6. **بوابة الجودة:**
   - CI: فحوص قاعدة البيانات بـ PGlite (`npm run test:db`: كل الترحيلات + فحوص الصلاحيات)، ثم typecheck وlint وbuild.
   - النشر يتم فقط بعد نجاحها.
   - كل سياسة أو دالة يرافقها فحص يفشل بدونها.
7. **الاستمرارية:**
   - Action مجدول يمنع خمول Supabase المجاني.
   - نسخة **يومية** بـ `pg_dump`، مشفّرة بـ `age`، تُحفظ Artifact لمدة 30 يومًا.
   - النسخ بدور `backup_reader` للقراءة فقط مع `bypassrls`.
   - لا بيانات عائلات غير مشفّرة في أي مستودع.
8. **الترحيلات:**
   - كل تعديل على القاعدة ترحيل في `supabase/migrations/`، بالتسلسل: يُختبر محليًا ← يمر في CI ← يُطبَّق ← يُعاد تسمية الملف بإصدار Supabase ← تُولَّد الأنواع (`src/types/database.ts`).
   - Prisma وترحيلاته يتقاعدان مع الخادم.
9. **عقل المشروع:**
   - `docs/HANDOFF.md` يُحمَّل لكل جلسة عبر `CLAUDE.md`، ويُحدَّث في نهاية كل جلسة.
   - أربعة مراجع فقط: HANDOFF وROADMAP وADR والجرد الوظيفي (`FUNCTIONAL_INVENTORY.md`).
   - باقي وثائق `docs/` تنتقل إلى `docs/archive/`.

## المراحل (لكل مرحلة بوابة، والتطبيق الحالي يعمل حتى تكتمل البوابة)

1. **الجرد:** `FUNCTIONAL_INVENTORY.md` يضم:
   - الميزات الحالية.
   - قواعد العمل BR-xx من الخادم واختباراته الـ 43.
   - ما لا يُنقل، مثل الفئات الفرعية التي لم تُخزَّن أصلًا.
   - قرارات علي Q-xx.
2. **المخطط والصلاحيات:** ترحيل أول (الجداول + القيود + RLS + دوال المال + سجل التدقيق) مع فحوص الصلاحيات. **البوابة:** كل الفحوص تنجح.
3. **الوثائق والإعداد:** HANDOFF وROADMAP وتحديث `CLAUDE.md`، ومشروع Supabase جديد يُنشأ **من supabase.com مباشرة**. المشروع الحالي `wazen-dev` أُنشئ عبر تكامل Vercel، وهذا من دروس المنهجية.
4. **الواجهة:** عميل Supabase واحد، وتحويل `src/services/` من axios إلى supabase-js، وتسجيل الدخول بـ Supabase Auth.
5. **CI والنشر:** **البوابة:** الموقع المنشور يقرأ من Supabase.
6. **النسخ الاحتياطي:** **البوابة:** أول نسخة ناجحة.
7. **التصدير إلى Google Sheets.**
8. **الإيقاف:** حذف `backend/` وPrisma وDocker بعد اكتمال كل البوابات.

## البدائل المرفوضة

- **إبقاء خادم Express مع استضافة (Render أو Fly):** خدمة ثالثة، وكلفة أو نوم في المجاني، وصلاحيات في الكود لا في القاعدة.
- **Next.js على Vercel:** لا حاجة لـ SSR ولا لمحركات البحث.
- **Firebase:** قاعدة غير علائقية لا تناسب صناديق وعمليات ومعاملات مالية.
- **نشر Pages من المستودع الخاص:** يحتاج اشتراكًا مدفوعًا.
- **حفظ نسخ القاعدة مكشوفة في git.**

## العواقب

- **صفر خادم يُدار وصفر كلفة ثابتة.** Supabase Pro (نحو 25$ شهريًا) اختياري عند الجدية.
- **إعادة كتابة المنطق المالي في SQL.** خطر أخطاء حسابية في الانتقال، تعالجه فحوص الصلاحيات والقواعد قبل كل مرحلة.
- **كل خطأ في RLS مكشوف للمتصفح،** لذلك فحوص الصلاحيات إلزامية.
- **لا SSR،** وهذا مقبول لتطبيق خلف تسجيل دخول.
