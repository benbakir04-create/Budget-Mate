# 0005: الاعتماد على Supabase وGitHub فقط

**التاريخ:** 16 نوفمبر 2026
**الحالة:** مقترح (Proposed). ينتظر موافقة علي قبل التنفيذ.
**يحلّ محل:** الجزء الخاص بالخادم في `TECHNICAL_ARCHITECTURE.md` (خادم Express مستقل)، ويعيد إحياء روح ADR 0003 بعد أن تجاوزها المشروع.

## السياق

البنية الحالية ثلاث قطع:

- واجهة React/Vite.
- خادم Express + Prisma يحتاج استضافة دائمة.
- قاعدة PostgreSQL على Supabase (مشروع `wazen-dev`، الباقة المجانية).

قبل أي استثمار، يريد علي أقل عدد من الخدمات وأقل كلفة: Supabase للبيانات والمنطق الحي، وGitHub عقلًا للمشروع ومنصة للنشر والواجهة، مع تصدير متحكَّم فيه إلى Google Sheets عند الحاجة.

## القرار

1. **Supabase هو الخادم:**
   - قاعدة البيانات.
   - المصادقة عبر Supabase Auth بدل JWT/bcrypt الحالي.
   - جدار الخصوصية بين المالك والشريك عبر سياسات RLS داخل القاعدة.
   - العمليات المالية (تمويل صندوق، صرف، اعتماد طلبية) دوال Postgres (RPC) تُنفَّذ في معاملة واحدة وتكتب سجل التدقيق.
   - Edge Functions لما لا يصلح داخل القاعدة، مثل التصدير.
2. **GitHub:**
   - الكود والوثائق وقرارات ADR والـ migrations (مجلد `supabase/migrations`).
   - الواجهة تُبنى وتُنشر على GitHub Pages عبر GitHub Actions مع كل دمج في `main`.
3. **Google Sheets:** تصدير يدوي يطلقه المالك وحده من زر في الإعدادات. يختار فيه الفترة والجداول، فتكتبها Edge Function إلى ورقة محددة بحساب خدمة (service account) مفتاحه في أسرار Supabase. لا مزامنة تلقائية.
4. **تجاوز الخمول والنسخ الاحتياطي (اقتراح علي)، عبر GitHub Actions مجدولة:**
   - **منع الخمول:** طلب خفيف إلى Supabase كل 3 أيام، حتى لا يتوقف المشروع المجاني إن لم يتفاعل المستخدمون.
   - **نسخة احتياطية أسبوعية:** `pg_dump` للقاعدة، **مشفّرة** بمفتاح في GitHub Secrets، تُحفظ في مستودع خاص منفصل (أو كـ artifact). الباقة المجانية لا تأخذ نسخًا احتياطية يمكن تنزيلها.
   - **ممنوع:** حفظ بيانات العائلات غير مشفّرة في أي مستودع git، خاصة إن صار مستودع الكود عامًا من أجل Pages.

## المراحل (التطبيق الحالي يبقى يعمل بينها)

1. **الأمان والمنطق:** Supabase Auth، وجداول المخطط الحالي عبر migrations في `supabase/`، وسياسات RLS، ودوال RPC للعمليات المالية مع اختبارات (pgTAP أو اختبارات تكامل على قاعدة تجريبية). ثم تحويل خدمات الواجهة (`src/services/`) إلى عميل Supabase.
2. **النشر:** GitHub Pages + Actions، مع معالجة توجيه الصفحات (SPA).
3. **الحماية التشغيلية:** منع الخمول، والنسخ الاحتياطي المشفّر.
4. **التصدير:** زر Google Sheets.
5. **الإيقاف:** إزالة `backend/` بعد أن تعمل كل المراحل وتُختبر.

## العواقب

**مزايا:**

- لا استضافة ثالثة.
- تحديث لحظي بين الشريكين.
- أمان على مستوى القاعدة.
- مصادقة متكاملة.
- نشر تلقائي.

**عيوب:**

- إعادة كتابة الخادم واختباراته الـ 43، مع خطر أخطاء حسابية في الانتقال يعالجه الاختبار قبل كل مرحلة.
- ارتباط أكبر بـ Supabase.
- منطق بلغة SQL أصعب صيانة.

**كلفة متوقعة عند الجدية:**

- Supabase Pro نحو 25$ شهريًا (نسخ احتياطية يومية ولا خمول).
- GitHub Pro نحو 4$ شهريًا إن بقي المستودع خاصًا.

**أسئلة مفتوحة:**

- هل يبقى المستودع خاصًا (Pro) أم يصبح عامًا؟
- أين تُحفظ النسخ الاحتياطية: مستودع خاص منفصل، أم Google Drive؟
- هل نهاجر بيانات `wazen-dev` الحالية أم نبدأ من قاعدة نظيفة؟ البيانات الحالية تجريبية.
